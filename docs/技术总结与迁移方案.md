# Kwrt 路由器 HTTPS 解密抓包系统 — 技术总结与迁移方案

> 项目位置：工作区 `pktcap/`（源码）+ 路由器 `/usr/share/{pktcap,mitm}/`（部署）
> 运行环境：Cudy TR3000 v1（MT7981 双核 aarch64）· Kwrt 25.12（OpenWrt 系）· 483MB 内存
> 代码规模：约 4200 行（Python 2487 + HTML 1768），**零第三方运行时依赖**

---

## 一、这是什么

一套**完全跑在路由器上**的 HTTPS 解密抓包系统，浏览器打开即用，不依赖电脑：

| 能力 | 说明 |
|------|------|
| 🔓 **HTTPS 解密** | 透明中间人（MITM），动态签发证书，能看请求/响应**正文**（含中文） |
| 👁 **网页查看** | 中文界面、JSON 自动美化着色、一键复制、状态码/方法徽标 |
| 🔍 **多角度搜索** | 多关键字（AND/OR）、正则、按设备/主机/类型/大小/时间、状态码筛选 |
| ↻ **重放 & 请求编辑器** | 一键重放某条请求；或复制请求后改头/改体再发（类 Apipost 简化版），可复制为 cURL |
| 🎛 **精细化控制** | 抓哪些设备（IP/CIDR）、哪些网卡、解密哪些域名（全解/白名单/排除） |
| 🩹 **证书固定自愈** | 解密失败的域名自动放行并连带其父域名，App 不会被"抓挂" |
| ⚡ **按需启停** | 抓包和解密**默认都关**，点了才跑；无人监听自动关闭，不占性能 |

## 二、技术栈

### 运行环境（路由器侧）

| 组件 | 版本 | 用途 | 备注 |
|------|------|------|------|
| OpenWrt / Kwrt | 25.12 | 系统 | 任何 OpenWrt 23.05+ 均可 |
| **Python** | 3.13.9（`python3-light`） | 两个服务的运行时 | ⚠️ 是裁剪版，详见下方约束 |
| `python3-openssl` | 随系统 | TLS 终结 | 提供 `ssl` 模块 |
| `python3-cryptography` | 随系统 | 动态签发叶子证书 | 唯一的"重"依赖 |
| **tcpdump** | 4.99.6 | 抓原始包（仅抓包表格用） | 可选，不装不影响解密 |
| OpenSSL | 3.5.7 | 生成 CA | `openssl-util` 包 |
| **nftables** | 内核自带 | 透明重定向 80/443 | OpenWrt 22.03+ 默认 nft |
| web 服务 | nginx（80 端口） | 仅托管证书下载页 | 解密系统自身**不需要**它 |

### 前端

纯原生 HTML/CSS/JS，**无任何框架、无构建步骤、无外部 CDN**（路由器环境常常断外网）。
SSE（Server-Sent Events）做实时推送，比 WebSocket 简单得多且够用。

### 为什么不用现成方案？

| 方案 | 为什么没用 |
|------|-----------|
| **mitmproxy** | OpenWrt 仓库没有打包；它是为桌面/服务器设计的，依赖重（aiohttp、h2 等），路由器装不动 |
| **squid + ssl_bump** | 试过，**只能记 URL，抓不到正文**，满足不了需求（已替换） |
| **sslsplit** | 仓库没有；且它只做解密不做 HTTP 语义解析，正文仍需另写解析器 |
| **Wireshark/tshark** | 路由器上跑不动，且是离线分析工具不是实时代理 |

**结论：在 OpenWrt 这个生态里，"自建"不是炫技，是唯一可行路径。** 全部用标准库手写，换来的是：
零 pip 依赖、约 90KB 代码 + 2 个进程、内存占用 ~30MB、可完整迁移。

### ⚠️ `python3-light` 的裁剪约束（迁移时的头号坑）

| 缺失/受限 | 影响 | 我们的对策 |
|-----------|------|-----------|
| **无 `email` 模块** | `http.server`、`http.client`、`urllib.request` **全部 import 失败** | Web 服务与 HTTP 客户端**全部用裸 socket 手写** |
| **无 `encodings.idna`** | `socket.getaddrinfo`/`ssl` 传 **str 主机名**会抛 `unknown encoding: idna` | 主机名一律 **传 bytes** |
| 无 `ssl`（默认） | 无法做 TLS | 需装 `python3-openssl` |
| `http.server` 不可用 | — | SSE 也是手写的 `text/event-stream` |

> 这几条是整个项目**最反直觉**的部分：在标准 Python 上能跑的代码，到这里全挂。
> 如果迁移到普通 Linux（Debian/Alpine），这些约束**自动消失**，代码只需微调。

## 三、架构与数据流

```
┌─────────────── 局域网设备（手机/PC） ───────────────┐
│  ① HTTP :80        ② HTTPS :443（TCP）  ③ QUIC :443(UDP) │
└────────┬───────────────┬──────────────────┬────────┘
         │               │                  │
   ┌─────▼───────────────▼──────────────────▼─────┐
   │  nftables（inet mitm 表，dstnat 钩子）          │
   │  · 按 src_addrs 集合过滤设备                    │
   │  · 按 src_ifaces 集合过滤来源网卡                │
   │  · :80  → redirect :8080                       │
   │  · :443 → redirect :8443                       │
   │  · udp 443 → drop（封 QUIC 逼回 TCP）           │
   └─────┬───────────────┬──────────────────────────┘
         │               │
   ┌─────▼─────┐   ┌─────▼──────────────────────────┐
   │ 8080 明文  │   │  8443（TLS 终结）                │
   │ HTTP 解析  │   │  · MSG_PEEK 窥探 SNI            │
   └─────┬─────┘   │  · SO_ORIGINAL_DST 取真实目标    │
         │         │  · cryptography 动态签发叶证书    │
         │         │  · 客户端拒证书 → 记入自动放行      │
         │         └─────┬──────────────────────────┘
         │               │
   ┌─────▼───────────────▼──────────────────────────┐
   │  mitm_proxy.py（转发 + 记录）                     │
   │  · 响应【逐字节流式转发】← 修复过截断 bug          │
   │  · 只抓前缀做记录（文本 256KB / 二进制 2KB）        │
   │  · 域名策略：all / list(白名单) / exclude(排除)    │
   │  · 写 /tmp/mitm-body.jsonl（4MB 上限自动裁剪）     │
   └───────────────────┬────────────────────────────┘
                       │ 尾随读取
   ┌───────────────────▼────────────────────────────┐
   │  pktcap_server.py（:7690 Web/API 服务）          │
   │  · SSE 实时推送 → body.html（解密内容页）          │
   │  · /api/send    → 重放 / 请求编辑器               │
   │  · /api/capture → 抓包按需启停                    │
   │  · /api/mitm    → 开关/范围/域名/自动关闭           │
   │  · /api/log     → 日志保留与清理                   │
   │  · 心跳判定「有人在看」→ 无人自动关闭解密            │
   └─────────────────────────────────────────────────┘
```

### 三种域名模式（对应不同使用场景）

| 模式 | 解密范围 | 证书固定的 App | 适用 |
|------|---------|---------------|------|
| `all` | 全部 | 首次失败后自动放行 | 尽量多抓 |
| `list` | **仅名单内** | 名单外全部正常 | **只盯某几个接口（推荐）** |
| `exclude` | 名单外全部 | 名单内正常 | 抓得全 + 指定 App 放行 |

## 五、难点与关键决策（踩过的坑）

按"解决问题的价值"排序，每条都是真实踩过的：

### 1. 响应截断 → App 白屏（最隐蔽、后果最重）
- **现象**：页面里能看到请求和响应正文，但 App 自己显示不出来。
- **取证**：服务器真实 `Content-Length: 263460`，记录里 `resp_len=200000`（正好是常量上限）。
- **根因**：先缓冲整个响应再重发，读的时候被 `min(n, MAX_BODY)` 截断，**又把 Content-Length 改写成截断后的长度** → 客户端以为收完了，实际 JSON 断在中间。
- **解法**：改为**逐字节流式转发**，`Content-Length/Content-Encoding/Transfer-Encoding` 原样保留，只"顺带抓前缀"做记录。
- **教训**：转发路径上任何 `min(n, LIMIT)`、任何"重新计算 Content-Length"都要警惕。

### 2. 证书固定的 App 被"抓挂"
- **现象**：一开解密，拼多多/淘宝/支付宝全连不上。
- **根因**：这些 App 做了 **SSL Pinning**，发现证书不对就拒绝连接。这是 TLS 机制，任何 MITM 都绕不过。
- **解法**：**自动放行自愈** —— 握手失败（`CERTIFICATE_UNKNOWN` 等）就把该域名记入放行名单，并**连带放行父域名**（`img.pddpic.com` → 放行 `pddpic.com`，一次覆盖几百个子域）。
- **配套**：`logread` 一行命令可从内核日志批量抢救已失败的域名。

### 3. `python3-light` 的 idna 缺失
- `socket.getaddrinfo` 传字符串主机名 → `LookupError: unknown encoding: idna`。
- 解法：主机名一律传 **bytes**（`host.encode("ascii")`）。这个坑在 MITM 转发、主动发请求两处都踩过。

### 4. 叶子证书缺扩展 → 客户端全拒
- 只带 SAN + BasicConstraints 的证书会被几乎所有客户端拒绝（`certificate unknown`）。
- 必须带齐：`KeyUsage(critical)` + `ExtendedKeyUsage(serverAuth)` + `SKI` + `AKI`。
- 弱 CPU 上**所有叶子证书共用一把 RSA 私钥**，只换证书主体，省掉每次几秒的密钥生成。

### 5. "有人在看"不能用连接数判断
- **现象**：自动关闭永远不触发，`viewers=5` 但根本没人看。
- **根因**：预览面板/休眠标签页的 SSE 连接一直挂着。
- **解法**：改成**心跳判定** —— 页面可见时每 30s `POST /api/ping`，服务端超过 90s 没收到就算"没人看"。

### 6. 控制台"选了又被弹回"
- 为了更新高亮，加了 `click → paint()`，而 `paint()` 会把服务端状态写回表单 → 用户点击被立刻撤销。
- **解法**：**刷新与表单回填解耦**——只有首次加载和保存成功后才回填；周期刷新只更新状态显示。

### 7. 换引擎后的"幽灵数据"
- 从 squid 换成自建代理后，squid 残留进程还在，旧日志页看着是空的。
- **解法**：杀残留、`disable` 旧服务、旧页面 302 到新页面、统一导航。

### 8. 无 SNI 的连接被静默丢弃
- 不带 SNI 的 TLS 连接原本直接 return（连接被丢）。
- 解法：把 `SO_ORIGINAL_DST` 拿到的原始 IP 作为兜底提示。

### 9. 非 HTTP 协议走 80 端口
- 腾讯系 App 的私有二进制协议走 TCP 80，被当 HTTP 解析出乱码记录。
- 解法：HTTP 请求行必须以大写字母开头 + 正则校验，不符则**原样透传**（`splice` 支持把已读字节补发回去）。

### 10. `/tmp` 是 tmpfs
- 记录文件只增不减 = 直接吃内存。加了 4MB 上限 + 只保留最近 400 条，原子替换。

## 六、性能设计（路由器上的生存法则）

| 设计 | 收益 |
|------|------|
| 抓包按需启动（默认关） | 不点就 0 个 tcpdump 进程 |
| 解密按需启动 + 无人监听自动关闭 | 平时 0 拦截、0 解密开销 |
| 响应流式转发，只抓前缀 | 内存占用与响应大小无关 |
| 日志 4MB 上限 + 400 条裁剪 | tmpfs 不会慢慢吃光内存 |
| SSE 历史回放限 60 条 | 进页面不再一次性推几 MB |
| 前端 DOM 上限 400 行、内存 2000 条 | 长时间跑不卡 |
| 轮询 20s + `document.hidden` 跳过 | 后台标签页零开销 |
| 所有叶子证书共用一把私钥 | 省掉每次 RSA 生成的数秒耗时 |

实测：**常驻 2 个 python 进程，内存 ~30MB**；抓包/解密都关时 CPU 接近 0。

## 七、安全边界与已知限制

### 必须知道的限制（不是 bug，是物理/协议限制）
1. **不做中间人就看不到 HTTPS 正文**（TLS 数学原理）。
2. **证书固定的 App 永远解不了正文**（但会被自动放行，App 正常用）。
3. Android 7+ **用户安装的 CA 只对浏览器生效**，多数 App 不认（需 root 装系统证书）。
4. 页面正文只保留前 2 万字符（转发给 App 的始终完整）。

### 安全设计
- 服务监听 LAN，防火墙规则**显式拒绝 WAN 访问 7690/8080/8443**。
- 所有 API 走 HTTP Basic Auth。
- CA 私钥只留在路由器，不随代码打包。
- ⚠️ 已知点：`/api/send` 是个"由路由器代发请求"的接口，本质是内网 SSRF 面——目前靠局域网边界保护，**如果要暴露到公网/ZeroTier，必须加权限或去掉**。

### ⚠️ 合规提醒
对他人设备做解密属高敏感操作。请仅在自己拥有/授权的网络与设备上使用。

## 八、迁移到其他系统：可行性矩阵

代码是**纯标准库 Python + 原生前端**，迁移成本低。关键是替换两处平台相关件：**流量重定向**和**服务管理**。

| 目标平台 | 可行性 | 重定向方式 | 服务管理 | 额外工作 |
|---------|--------|-----------|---------|---------|
| **OpenWrt 系路由器**（同/异架构） | ★★★★★ | nftables（已有） | procd（已有） | 基本零改动 |
| **OpenWrt 21.02 及更早** | ★★★☆☆ | 换 iptables REDIRECT | procd | 需写 iptables 版脚本 |
| **Debian / Ubuntu（x86/ARM）** | ★★★★★ | nftables 或 iptables | systemd | 写 unit 文件 + 重定向脚本 |
| **Docker 容器** | ★★★★★ | 容器内 nft（需 NET_ADMIN） | docker compose | 最推荐，见下 |
| **macOS** | ★★★☆☆ | pf（`packet filter`）anchors | launchd | 重定向要重写 |
| **Windows** | ★★☆☆☆ | WinDivert / 系统代理 | 计划任务/服务 | 透明代理较麻烦，**建议走显式代理模式** |
| **群晖/威联通 NAS** | ★★★★☆ | iptables | systemd/upstart | 走 Docker 更省事 |
| **普通 Linux + 显式代理** | ★★★★★ | 不需要 | systemd | **零改动**：设备手动把代理指向 `IP:8080` |

### 迁移要点

1. **两种工作模式，决定迁移难度**
   - **透明模式**（现在的样子）：需要平台的重定向能力（nft/iptables/pf/WinDivert）。
   - **显式代理模式**：设备在 WiFi 里填代理 `IP:8080` → **任何系统都能跑，零平台依赖**。
     代码已支持（8080 同时是显式代理端口）。迁移到陌生系统时优先用这个，跑通再考虑透明。

2. **必须替换的**（都有清晰边界）
   - `nft` 调用 → 平台等价物
   - `/etc/init.d/*` → systemd unit / launchd plist / docker-compose
   - 路径：`/etc/mitm/`、`/usr/share/{pktcap,mitm}/` → 单一配置目录（建议都归到 `/etc/kwrtcap/`）

3. **迁移后立刻变好的**
   - 普通 Python 有 `email` 模块 → 可以把裸 socket 的 HTTP 解析换成 `http.client`（更稳）
   - 有 idna → 主机名可以传 str（现有 bytes 写法仍然兼容，可不改）
   - 磁盘不再是 tmpfs → 日志上限可以放宽

## 九、打包方案（四选一，可组合）

### 方案 A：OpenWrt `.ipk` 包（最贴合现状）⭐ 推荐给路由器用户

把现有部署固化成一个可 `opkg install` 的包。

- **结构**：
  ```
  kwrtcap_1.0.0_aarch64.ipk
  ├── control/           (控制文件：依赖 python3-light python3-openssl python3-cryptography tcpdump)
  ├── data/usr/share/kwrtcap/   (py + html)
  ├── data/etc/kwrtcap/         (默认配置)
  ├── data/etc/init.d/kwrtcap   (procd 服务，一个服务拉起两个进程)
  └── data/usr/bin/kwrtcap-ctl  (合并 mitm-ctl 与抓包开关)
  ```
- **优点**：`opkg install` 一条命令；依赖自动解决；升级干净。
- **工作量**：约 1 天（主要是写 `control` 和把两个 init 合并）。
- **注意**：CA 首次启动时自动生成，私钥不进包。

### 方案 B：Docker 镜像（最通用）⭐ 推荐给 NAS/服务器用户

- **结构**：
  ```dockerfile
  FROM python:3.12-alpine
  RUN apk add --no-cache tcpdump nftables iptables openssl
  COPY . /app
  EXPOSE 7690 8080 8443
  ENTRYPOINT ["python3", "/app/pktcap_server.py"]
  ```
  + `docker-compose.yml`（`cap_add: NET_ADMIN`、`network_mode: host` 以便拿到原始目标地址）
- **优点**：一条 `docker compose up` 在 x86/ARM NAS、软路由、云主机上都能跑；环境完全自包含。
- **限制**：容器内做透明代理需要 `NET_ADMIN` + `host` 网络；树莓派等 ARM 也没问题（镜像多架构）。
- **工作量**：约半天。

### 方案 C：单目录 tarball + systemd（最简单直接）

```
kwrtcap-1.0.0-linux.tar.gz
├── kwrtcap/            (py + html + 配置模板)
├── kwrtcap.service     (systemd unit，含 AmbientCapabilities=CAP_NET_ADMIN)
├── 30-kwrtcap.nft      (nft 规则文件，nft -f 加载)
└── install.sh          (拷文件、启服务、装规则、打印证书下载地址)
```
- **优点**：不依赖包管理器，`tar xzf && ./install.sh` 两步。
- **工作量**：约半天。

### 方案 D：显式代理模式"绿色版"（零权限、最容易分享）

- 只带 Web/API + 代理，**不做透明拦截**；用户在设备 WiFi 里手动填代理。
- 优点：不需要 root/CAP_NET_ADMIN，Windows/macOS 都能跑，最适合给别人试用。
- 缺点：没法"自动抓全 LAN"，只对配置了代理的设备生效。
- 工作量：几乎为零（现有代码去掉 nft 部分即可）。

### 建议的组合拳

1. **先做 D**（半天内完成，能立刻分享给别人用）
2. **再做 A**（服务你自己的 OpenWrt 生态，一条命令部署）
3. **有余力做 B**（覆盖 NAS/软路由/云主机最大人群）
4. C 作为 B 的替代，给不想用 Docker 的人
